the card vault

The goal: an agent can pay for something online with your card, and the model never sees the card number. So a prompt injection, a leaked transcript or a chatty model cannot give it away.

You hand over a card for named sites. The system stores it where the agent cannot read it, and the agent only ever holds an opaque handle. The code is vault/cardvault/.

the flow

01
You ask for something.
can you order this for me on Amazon?
02
The agent asks which sites the card may be used on and calls card_request. Then it asks for the number, expiry and security code in one text.
03
You text the card. Before the agent runs, the gateway hook hands the text to the intake. The details go into the encrypted vault, one item per allowed site, and the message is replaced with a note. That note is all the model and the transcript ever get.
04
At checkout the agent must call checkout_start, which makes it ask first: just for you, or a group order to split before paying? Solo is cleared. A group order opens a prepay split, and the checkout only clears once the split plugin reports it fully collected.
05
The fill. The guard checks the card is yours and the purchase is cleared. The runtime asks you to confirm. Then the card is typed into the page without passing through the model.

can and cannot

canAsk for a card, list a person's cards, delete one, request a fill on an allowed site
cannotRead a card back, fill it on another site, fill someone else's card, fill without a cleared purchase and the person's confirmation

ours and theirs

The runtime in core/ already ships the hard part: an encrypted store, handles the model can list but not read, a fill that only works on the exact site a card is bound to, and redaction of filled values. That vault assumes one person adding cards from a terminal. GroupCart is many people, over text. We added:

ourswhat it does
Intake over textCatches card details in an inbound message before the model or the transcript sees them
Permitted sitesThe person names the sites first; the card is bound to exactly those
Per-person scopingYou only see and fill vault items you saved
Checkout gateA card fill needs a cleared purchase: solo, or a group order whose split is fully paid
Second netCard numbers are stripped from every model request and tool result

honest limits

  • The card travels over iMessage and through Photon to reach us. It is kept out of the model, the transcript and our state file, but it exists in your own message history and in transit. One-time virtual cards per purchase are the right next step.
  • Not tested end to end by us: the actual fill into a live checkout page, and the confirmation prompt as it appears over iMessage. Both are runtime features.
  • Exact sites only. A checkout hosted on a third domain is refused until that site is added.
  • The vault key sits next to the vault file on the machine. Anyone with the laptop has both.
